# Friction Log

Entries are written when problems happen, not reconstructed later.
Severity: **Critical** (blocked) · **High** (design change or major workaround) · **Medium** (slowed down) · **Low** (annoyance).
Status: **Open** · **Workaround** (in use) · **Resolved**.
Evidence files live in `docs/evidence/` and are sanitized (no tokens, no device/account IDs).

# Developer tools and APIs

## FL-01: Playground Motion/Vehicle/Package triggers are all recorded as `on_demand`
| | |
|---|---|
| Date tested | 2026-09-21 |
| Environment / endpoint | Ring Developer Playground token · `GET https://api.amazonvision.com/v1/history/devices/{device_id}/events` |
| Docs | [Event History](https://developer.amazon.com/docs/ring/api-documentation.html) · [Release notes (Playground, 2026-05-28)](https://developer.amazon.com/docs/ring/release-notes.html) |
| Evidence | `docs/evidence/FL-01_playground_triggers_on_demand.json` |
| Status | Workaround |

- **Task attempted:** Capture Ring motion events with a person/vehicle classification to drive the dealership zones.
- **Steps taken:** Generated a Playground token → triggered Motion, Vehicle, and Package (three rounds) → called Event History from `scripts/ring_capture.py`.
- **Expected result:** History events with `event_type: "motion"` and subtypes (`motion.human`, `motion.vehicle`), as the Event History docs describe.
- **Actual result:** HTTP 200 with 8 events, all `event_type: "on_demand"` and `cv_detections: []`. Nothing identifies which trigger was pressed. The docs define `on_demand` as a live-view session.
- **Severity:** High. The zone design had to change.
- **Workaround:** Treat each Ring event as generic camera activity. In production, the zone comes from each device's configured placement. In Playground Demo Mode, the operator arms the single synthetic device for one of four camera positions (three zones) before triggering an event.
- **Suggestion:** Record Playground triggers as `motion` events with the matching subtype (and emit a simulated `motion_detected` webhook), or at least label the simulated trigger type on the history record.

## FL-02: `event_types` filter is ignored for Playground events
| | |
|---|---|
| Date tested | 2026-09-21 (initial test + controlled re-test) |
| Environment / endpoint | Ring Developer Playground token · `GET /v1/history/devices/{device_id}/events?event_types=…` |
| Docs | [Event History, event type filtering](https://developer.amazon.com/docs/ring/api-documentation.html) (documented syntax: comma-separated, dot-delimited subtypes, e.g. `event_types=motion.vehicle,motion.human`) |
| Evidence | `docs/evidence/FL-02_event_types_filter_test.json` (generated by `scripts/ring_filter_test.py`) |
| Status | Open |

- **Task attempted:** Filter history to motion subtypes to check whether any classified events existed.
- **Steps taken:** Called the endpoint with single values `motion`, `motion.human`, `motion.vehicle`, `motion.package`, `on_demand`. Controlled re-test (script above) adds the exact documented composite example `motion.human,motion.vehicle`, a control `ding` (no doorbell presses were made), and an invalid value `not_a_real_type`.
- **Expected result:** Motion and `ding` filters return 0 events (only `on_demand` exists); `on_demand` returns all; the invalid value returns 400 or 0.
- **Actual result:** Every query returned HTTP 200 with the same 8 `on_demand` events: no filter, the documented composite `motion.human,motion.vehicle`, `motion`, `ding` (no doorbell presses were ever made), `on_demand`, and the invalid `not_a_real_type`. The filter had no effect and invalid values were not rejected.
- **Severity:** Medium. Misleading while debugging; counts would be wrong if the filter were trusted.
- **Workaround:** Don't rely on the filter; classify client-side on `attributes.event_type`.
- **Suggestion:** Apply the filter for Playground devices, or return 400 for unsupported values instead of ignoring them silently.

## FL-03: Only one synthetic device in the Playground
| | |
|---|---|
| Date tested | 2026-09-21 |
| Environment / endpoint | Ring Developer Playground token · `GET https://api.amazonvision.com/v1/devices` |
| Docs | [Device Discovery / Multi-Camera Devices](https://developer.amazon.com/docs/ring/api-documentation.html) · [Release notes](https://developer.amazon.com/docs/ring/release-notes.html) |
| Evidence | `docs/evidence/FL-03_single_playground_device.json` |
| Status | Workaround |

- **Task attempted:** Map three dealership zones to separate Ring cameras.
- **Steps taken:** Listed devices with a Playground token; searched the docs and Playground UI for a way to add devices.
- **Expected result:** Several synthetic devices, or a synthetic multi-camera device with `components`.
- **Actual result:** One device ("Playground Device", Doorbell Pro image, no `components`). No documented way was found to add another synthetic device.
- **Severity:** High. It blocks direct multi-zone testing.
- **Workaround:** Time-bounded demo arming of the single device for one camera position, clearly labeled in the UI and README. Production gives each device one configured placement.
- **Suggestion:** Allow multiple synthetic devices, or a synthetic Ring Elite-style device with `component_ids`, in the Playground.

## FL-04: No documented webhook path with a Playground token
| | |
|---|---|
| Date tested | 2026-09-21 |
| Environment / endpoint | Ring Developer Playground token · Webhook v1.1 |
| Docs | [Notifications](https://developer.amazon.com/docs/ring/api-documentation.html) · [ring-api-helloworld README](https://github.com/AmazonAppDev/ring-api-helloworld) |
| Evidence | Documentation review only: helloworld README lists webhook events under refresh-token mode; Notifications docs require a Webhook URL registered in the Developer Portal |
| Status | Workaround |

- **Task attempted:** Receive real-time events instead of polling.
- **Steps taken:** Reviewed the helloworld README, the Notifications docs, and the Playground for a webhook option.
- **Expected result:** A way to send Playground events to a test webhook URL.
- **Actual result:** The temporary Playground token does not provide a documented path for configuring or testing webhook delivery.
- **Severity:** Medium.
- **Workaround:** Poll Event History, which the docs describe as the "API polling alternative". The webhook handler is built to spec for when a registered app is available.
- **Suggestion:** A Playground webhook tester that sends signed sample `motion_detected` payloads to a developer-provided URL, or shows the exact payload that would have been sent.

## FL-05: History and webhook payloads describe the same event differently
| | |
|---|---|
| Date tested | 2026-09-21 |
| Environment / endpoint | Event History (real responses) vs. Webhook v1.1 (documented payloads) |
| Docs | [Event History](https://developer.amazon.com/docs/ring/api-documentation.html) · [Motion Detection webhook](https://developer.amazon.com/docs/ring/api-documentation.html) |
| Evidence | `docs/ring-sample-payloads/example_history_event.json` vs. documented webhook example |
| Status | Workaround |

- **Task attempted:** Design one normalizer for both ingestion paths.
- **Steps taken:** Compared real history payloads with the documented webhook payloads.
- **Expected result:** Consistent field names across both surfaces.
- **Actual result:** History uses `attributes.event_type` + `start`/`end` + `relationships.source.data.id`. Webhooks use `data.type` + `attributes.timestamp` + `attributes.source`. Subtype lists differ: history lists `motion.animal`; the webhook `sub_type` table lists `motion`, `human`, `vehicle`, `other_motion`. This is integration friction, not necessarily a bug.
- **Severity:** Low.
- **Workaround:** One internal camera-activity schema with a mapper per source.
- **Suggestion:** Publish a mapping table between history and webhook fields and align the subtype lists.

## FL-07: Bedrock output needs explicit tone and grounding constraints
| | |
|---|---|
| Date tested | 2026-09-21 |
| Environment / endpoint | Amazon Bedrock Converse API · `amazon.nova-micro-v1:0` · us-east-1 · temperature 0 |
| Docs | [Bedrock Converse API](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html) |
| Evidence | `docs/evidence/FL-07_bedrock_tone_test.json` |
| Status | Workaround (Phase 4 prompt design) |

- **Task attempted:** Hello-world call to confirm Bedrock access.
- **Steps taken:** User prompt: `Say hello to DealerSight in one sentence.` Run twice at temperature 0: once without a system prompt, once with a tone system prompt.
- **Expected result:** A plain, factual one-sentence greeting.
- **Actual result:**
  - Without a system prompt (reproducible): *"Discover DealerSight, the innovative platform revolutionizing vehicle dealership operations with cutting-edge technology and seamless solutions."*
  - With a tone prompt ("plain, factual… no promotional language… under 20 words"): tone was fixed, but the model **invented a product description**: *"DealerSight provides vehicle inspection and valuation services."* (it was given no facts about DealerSight).
- **Severity:** Low for the spike; important for Phase 4 design.
- **Workaround:** The analyst gets a structured metric packet as its only source of facts, a system prompt that forbids unsupported claims, an explicit `insufficient data` path, and a check that every number in the answer appears in the packet.
- **Suggestion:** Document grounding and tone best practices per model in the Bedrock model catalog, e.g. an example system prompt for "explain only these provided facts" use cases.
